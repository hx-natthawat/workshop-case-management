## 2. User stories (Phase 1)

### ผู้แจ้ง (Reporter)

**R1 ลงทะเบียนพร้อมความยินยอม (M)** ในฐานะผู้แจ้ง ฉันต้องการลงทะเบียนครั้งเดียว เพื่อแจ้งเคสได้โดยไม่ต้องกรอกข้อมูลติดต่อซ้ำ
- Given ผู้ใช้เพิ่มเพื่อน OA When ระบบได้รับ `follow` Then bot ส่งข้อความต้อนรับพร้อมปุ่ม "ลงทะเบียน"
- Given เปิดหน้าลงทะเบียน When ไม่ติ๊กยินยอม Then ส่งฟอร์มไม่ได้
- Given กรอกเบอร์ผิดรูปแบบ When ส่ง Then แสดงข้อผิดพลาดใต้ช่อง
- Given ลงทะเบียนสำเร็จ Then บันทึก `consent_version` และ `consent_at` และ bot ส่งเมนูเริ่มต้น
- Given ผู้ใช้ยังไม่ลงทะเบียน When กด "แจ้งปัญหาใหม่" Then bot ขอให้ลงทะเบียนก่อน
- PDPA: แสดงวัตถุประสงค์การเก็บข้อมูลก่อนเก็บ ยืนยันตัวตนบน LINE จริงด้วย ID token

**R2 แจ้งเคสตามแบบฟอร์ม (L)** ในฐานะผู้แจ้ง ฉันต้องการตอบคำถามทีละข้อ เพื่อให้เจ้าหน้าที่ได้ข้อมูลครบตั้งแต่ครั้งแรก
- Given เลือกหมวดหลักและหมวดย่อย Then bot ถามข้อ 1 พร้อมบอก "ข้อ 1 จาก N"
- Given คำถามแบบตัวเลือก Then แสดง Quick Reply และรับทั้งการกดและการพิมพ์ที่ตรงกับตัวเลือก
- Given ตอบผิดรูปแบบ 3 ครั้ง Then bot เสนอ "คุยกับเจ้าหน้าที่" หรือ "เริ่มใหม่"
- Given พิมพ์ `ย้อนกลับ` Then กลับไปข้อก่อนหน้าที่แสดงจริง · `เริ่มใหม่` เริ่มเลือกหมวด · `ยกเลิก` ล้างร่าง
- Given ไม่ตอบเกิน 30 นาที Then ร่างหมดอายุ · กลับมาภายใน 30 นาทีแล้วกด "แจ้งปัญหาใหม่" Then ถามว่าจะทำต่อหรือเริ่มใหม่
- Given คำถามแบบมีเงื่อนไขอย่างง่าย (`show_if` เท่ากับค่า) Then ข้ามข้อที่ไม่ตรงเงื่อนไข

**R3 แนบรูปและสรุปก่อนยืนยัน (M)**
- Given คำถามแนบไฟล์ When ส่งรูปหลายรูป Then ระบบรับจนกด "เสร็จ" ไม่เกินจำนวนที่กำหนด
- Given ตอบครบ Then แสดง Flex สรุปพร้อมปุ่ม ยืนยัน · แก้ไขข้อ · ยกเลิก
- Given กด "แก้ไขข้อ" Then เลือกข้อที่จะแก้ ตอบใหม่ แล้วกลับมาที่สรุป
- Given กดยืนยัน Then ได้เลขเคสและเวลาที่คาดว่าจะได้รับการตอบรับตาม SLA ภายในข้อความตอบกลับเดียว (Reply)

**R4 เคสของฉันและติดตามสถานะ (M)**
- Given กด "เคสของฉัน" Then แสดงเคสที่ยังไม่ปิดเป็น carousel พร้อมสถานะและผู้รับผิดชอบ (ไม่เกิน 10 ใบ)
- Given พิมพ์เลขเคสของตนเอง Then แสดงรายละเอียด · เลขเคสของคนอื่น Then แจ้งว่าไม่พบ

**R5 โต้ตอบกับเจ้าหน้าที่ (M)**
- Given เคสอยู่ใน `pending_customer` 1 เคส When ผู้แจ้งพิมพ์หรือส่งรูป Then ผูกเข้ากับเคสนั้นและเปลี่ยนเป็น `in_progress` SLA นับต่อ
- Given มีหลายเคสรอข้อมูล Then ให้เลือกเคสก่อน
- Given เจ้าหน้าที่ตอบทาง LINE Then ผู้แจ้งได้รับข้อความ (Push)

**R6 ประเมินความพึงพอใจและเปิดเคสใหม่ (M)**
- Given เคสเปลี่ยนเป็น `resolved` Then ผู้แจ้งได้รับการ์ดถามว่าแก้ไขเรียบร้อยหรือไม่
- Given กด "เรียบร้อยแล้ว" Then เคสเป็น `closed` และถามคะแนน 1–5 · บันทึก `csat_score`
- Given กด "ยังไม่เรียบร้อย" ภายใน 7 วัน Then เคสเป็น `reopened` และ `reopen_count` +1 · เกิน 7 วัน Then แนะนำให้แจ้งเคสใหม่
- Given ไม่ตอบ 3 วัน Then ระบบปิดเคสอัตโนมัติ

### เจ้าหน้าที่ (Agent)

**A1 Case Inbox (M)** ดูรายการเคสพร้อมแท็บ ของฉัน · ทีมของฉัน · ยังไม่มอบหมาย · ทั้งหมด และตัวกรองสถานะ priority หมวด และ "ใกล้/เกิน SLA"
- เบอร์โทรในรายการถูกปิดบังเสมอ · แถวที่เกิน SLA มีสีพื้นแดงอ่อน
- Agent เห็นเฉพาะเคสของตนเองและเคสที่ยังไม่มอบหมายในทีม (ตามตารางสิทธิ์ SPEC §5)

**A2 Case Detail และตอบกลับ (L)**
- เห็นคำตอบของแบบฟอร์มตาม version ที่บันทึกไว้ · timeline ข้อความ LINE บันทึกภายใน และเหตุการณ์ระบบ
- ตอบทาง LINE ได้ · ข้อความแรกที่ส่งบันทึก `first_response_at` · บันทึกภายในไม่ส่งถึงผู้แจ้ง
- เลือก "หลังส่ง" เปลี่ยนสถานะได้ในครั้งเดียว · ใช้ข้อความสำเร็จรูปได้
- กด "แสดง" เบอร์เต็มแล้วบันทึก audit log
- ดูรูปแนบผ่าน signed URL ที่หมดอายุ

**A3 เปลี่ยนสถานะและ priority (M)** เปลี่ยนได้เฉพาะตามตาราง state machine (04-design §4) · เปลี่ยน priority ต้องระบุเหตุผล · ทุกการเปลี่ยนบันทึก `case_event` และ `audit_log`

### หัวหน้าทีม (Supervisor)

**S1 มอบหมายงาน (M)** มอบหมายเองได้ · ระบบมอบหมายแบบ round-robin ให้สมาชิกทีมเมื่อสร้างเคส (เปิด/ปิดได้ต่อทีม)
**S2 Dashboard (M)** เคสเปิดอยู่ · ใกล้เกิน SLA · เกิน SLA · ยังไม่มอบหมาย · CSAT เฉลี่ย · เคสใหม่ 14 วัน
**S3 รายงาน 4 รายการและ export (M)** ปริมาณเคสตามหมวด · อัตราผ่าน SLA · เวลาตอบรับ/แก้ไขเฉลี่ย · CSAT · export CSV (บันทึก audit log ทุกครั้งเพราะมีข้อมูลส่วนบุคคล)
**S4 ปิดเคสโดยไม่รอผู้แจ้ง (S)** จาก `resolved` เป็น `closed` ได้ทันที

### ผู้ดูแลระบบ (Admin)

**D1 Bot Flow Builder แบบรายการ (L)** จัดการหมวด 2 ระดับ (ชื่อ · priority เริ่มต้น · ทีม) · แก้คำถามใน draft (ชนิด · label · key · บังคับตอบ · ตัวเลือก · validation · show_if อย่างง่าย) · publish เป็น version ใหม่ · บทสนทนาที่ค้างอยู่ใช้ version เดิม
**D2 ข้อความสำเร็จรูป (S)** เพิ่ม/แก้/ลบข้อความสำเร็จรูปของ agent
**D3 Users & Roles (M)** เพิ่มผู้ใช้ · กำหนดบทบาทและทีม · ปิดการใช้งาน
**D4 Audit log (M)** ดูบันทึกการเปลี่ยนแปลงและการดูข้อมูลส่วนบุคคล

## 3. Edge cases ที่ MVP ต้องรองรับ

| กรณี | การจัดการ |
| --- | --- |
| LINE ส่ง event ซ้ำ | เก็บ `webhookEventId` ใน `processed_event` (unique) ประมวลผลครั้งเดียว |
| ผู้ใช้บล็อก OA กลางเคส | `unfollow` → `contact.status = unfollowed` · Push ถูกข้ามและบันทึกใน timeline ว่าส่งไม่ได้ |
| ร่างหมดอายุ 30 นาที | `dialog_session.expires_at` · ข้อความหลังหมดอายุเริ่มต้นใหม่ |
| Publish ฟอร์มใหม่ระหว่างบทสนทนา | session เก็บ `form_version_id` · เคสบันทึก version และ `label_snapshot` |
| หลายเคส `pending_customer` | ให้เลือกเคสด้วย Quick Reply |
| SLA ข้ามวันหยุด | MVP นับเฉพาะเสาร์-อาทิตย์เป็นวันหยุด · วันหยุดนักขัตฤกษ์อยู่ใน Phase 2 |
| P1 นอกเวลาทำการ | นับ 24/7 |
| Reply token หมดอายุ (ประมวลผลช้า) | ถ้า Reply ล้มเหลวให้ fallback เป็น Push |

## 4. MVP cut (MoSCoW)

**Compliance must-have (ตัดไม่ได้):** ความยินยอม PDPA พร้อม version · ปิดบังเบอร์ในรายการ · audit log การดู/export/แก้ไขข้อมูลส่วนบุคคล · ตรวจลายเซ็น webhook · signed URL ไฟล์แนบ · rate limit ต่อ userId

| ลำดับ | รายการ |
| --- | --- |
| Must | R1–R6 · A1–A3 · S1–S3 · D1 · D3 · D4 · LINE simulator สำหรับทดสอบ · SLA sweep (80% · เกิน · ปิดอัตโนมัติ) · แจ้งเตือนในเว็บ |
| Should | S4 · D2 · หน้า Contacts แบบอ่านอย่างเดียว |
| Could | Rich menu บน OA จริงผ่านสคริปต์ · แจ้งเตือนทางอีเมล |
| Won't (MVP นี้) | OTP · SSO/OIDC (ADR 0003) · FAQ ก่อนเปิดเคส · รวมเคสซ้ำ · outbound webhook · Public API · วันหยุดนักขัตฤกษ์ · Flex template editor · broadcast · การแจ้งเตือนเข้า LINE กลุ่มทีม · ระยะเวลาเก็บรักษาอัตโนมัติ · คำขอของเจ้าของข้อมูลผ่านหน้า Contacts |

รายการ Won't ที่เป็นข้อกำหนด PDPA (ระยะเวลาเก็บรักษา · คำขอของเจ้าของข้อมูล) ยอมรับได้เฉพาะรอบทดสอบที่ใช้ข้อมูลสมมติ ต้องทำก่อนใช้งานจริง

## 5. คำถามที่ยังเปิดอยู่ (ไม่ขวาง MVP ทดสอบ)

ทุกข้อใน SPEC §9 ยังเปิดอยู่ MVP ใช้ค่าสมมติจาก `prototype/mock-data/` สำหรับหมวด แบบฟอร์ม และ SLA และตั้งค่าเป็น single-tenant ที่มี `tenant_id` ทุกตาราง
