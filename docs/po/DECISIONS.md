# บันทึกการตัดสินใจ (Decision Log)

ตั้งแต่ 30 ก.ย. 2569 Fero มอบหมายให้ PO ค้นข้อมูลและตัดสินใจเองตามกระบวนการ `/po` (SKILL.md กติกา 0a) ทุกการตัดสินใจบันทึกที่นี่ Fero กลับคำตัดสินใจได้ทุกข้อ โดยเพิ่มรายการใหม่อ้างถึงข้อเดิม

เรื่องที่ PO ยังต้องถาม Fero ก่อนดำเนินการ: การใช้เงินหรือสมัครแพ็กเกจที่มีค่าใช้จ่าย · การรับรองด้านกฎหมาย/PDPA · การกระทำที่ย้อนกลับไม่ได้หรือเผยแพร่ออกภายนอก (merge เข้า `main` · เผยแพร่ SPEC ฉบับแชร์ · ส่งข้อความถึงบุคคล · ลบข้อมูล) · ข้อเท็จจริงของลูกค้าที่ PO ไม่อาจรู้เอง

รูปแบบ: ID · วันที่ · คำถาม · ทางเลือก · การตัดสินใจ · หลักฐาน · ย้อนกลับได้หรือไม่ · งานต่อเนื่อง

## D-001 · อนุมัติ stage 3–6 สำหรับ MVP ทดสอบกับผู้ใช้
- **วันที่:** 2026-09-30 · **ที่มา:** STATUS.md "Decisions awaiting the user"
- **คำถาม:** เอกสาร analysis · design · plan และ ADR ฉบับย่อพร้อมใช้เป็นฐานของ MVP หรือไม่
- **ทางเลือก:** (ก) อนุมัติตามที่เป็น (ข) ทำฉบับเต็มก่อนอนุมัติ
- **การตัดสินใจ:** (ก) อนุมัติ stage 3–6 สำหรับขอบเขต "ทดสอบกับผู้ใช้ด้วยข้อมูลสมมติ"
- **หลักฐาน:** stage 8 ยืนยันว่าระบบที่สร้างตามเอกสารชุดนี้ผ่าน AC ของ Phase 1 ทุกข้อ (ยกเว้นข้อที่ waived) ดู `08-verify-mvp.md`
- **ย้อนกลับได้:** ได้ เอกสารแก้ไขได้ตามผลทดสอบ
- **งานต่อเนื่อง:** ทำฉบับเต็มของ design (routing · escalation · วันหยุด) เมื่อเริ่ม Phase 2

## D-002 · รับ ADR 0001–0005 เป็น `Accepted` (ขอบเขต MVP ทดสอบ)
- **วันที่:** 2026-09-30
- **การตัดสินใจ:** เปลี่ยนสถานะ ADR ทั้ง 5 เป็น `Accepted` โดยจำกัดขอบเขตที่การทดสอบกับผู้ใช้ ADR 0001 (Next.js แอปเดียว) · 0003 (login รหัสผ่าน) · 0004 (เก็บไฟล์บนดิสก์) ต้องมี ADR ใหม่มาแทนก่อนใช้งานจริง
- **หลักฐาน:** ผลวัด NFR และ security review ใน `08-verify-mvp.md` ไม่พบปัญหาที่เกิดจากการตัดสินใจเหล่านี้ในขอบเขตทดสอบ
- **ย้อนกลับได้:** ได้ ด้วย ADR ใหม่ (superseded)

## D-010 · คำตอบที่กำหนดเป็น P1 ปรับเคสเป็น P1 ได้ทันที (F-02)
- **คำถาม:** กติกา "ปรับขึ้นได้ 1 ระดับ" ทำให้เคสที่ "ทั้งหน่วยงานใช้งานไม่ได้" ในหมวด P3 ได้เพียง P2
- **ทางเลือก:** (ก) คงกติกาเดิม ให้เจ้าหน้าที่ปรับเอง (ข) ยกเว้นเฉพาะคำตอบที่ Admin กำหนดเป็น P1 (ค) ใช้ matrix impact × urgency เต็มรูปแบบ
- **การตัดสินใจ:** (ข) คำตอบที่ Admin ผูกกับ P1 ปรับเป็น P1 ได้ทันที คำตอบอื่นยังปรับได้ไม่เกิน 1 ระดับ
- **หลักฐาน:** ServiceNow และ Jira Service Management กำหนด priority จาก impact × urgency ไม่ใช่จากหมวด ผลกระทบวงกว้างที่เร่งด่วนได้ระดับสูงสุด (Q1) · SLA ตอบรับ P1 คือ 15 นาที การรอเจ้าหน้าที่ปรับเองอาจใช้เวลาเกินนั้น
- **ย้อนกลับได้:** ได้ · (ค) เป็นงาน Phase 2 ร่วมกับ routing rule

## D-011 · SLA แบบเวลาทำการหยุดนับนอกเวลาทำการและนับต่อวันทำการถัดไป (F-09)
- **ทางเลือก:** (ก) ถือว่าเกินทันทีเมื่อเลยเวลาครบกำหนด (ข) หยุดนับนอกเวลาทำการ เกินเมื่อเวลาทำการเลยกำหนด
- **การตัดสินใจ:** (ข) สำหรับ P2–P4 ส่วน P1 นับ 24/7 ตามนาฬิกาจริง
- **หลักฐาน:** Zendesk · Freshdesk · Jira Service Management หยุดนับนอกเวลาทำการและยกเวลาที่เหลือไปวันทำการถัดไป (Q2) · สอดคล้องกับ SPEC §4 "นับเฉพาะเวลาทำการ"

- **ย้อนกลับได้:** ได้

## D-012 · ยังไม่ดึง FAQ ก่อนเปิดเคสเข้า MVP รอบทดสอบแรก (F-12)

- **การตัดสินใจ:** (ข) เพิ่มคำถามในสคริปต์ทดสอบเพื่อวัดว่าผู้แจ้งต้องการคำแนะนำก่อนแจ้งหรือไม่ แล้วตัดสินใหม่หลังรอบแรก
- **หลักฐาน:** vendor แสดงบทความระหว่างกรอกคำขอ แต่ตัวเลขความสำเร็จเป็นของ vendor เอง · Gartner (2024) พบว่าปัญหาที่แก้จบด้วยตนเองมีเพียง 14% (ยืนยันผ่านแหล่งรองเท่านั้น) · ไม่มีหลักฐานเฉพาะ LINE bot (Q3) · ต้องสร้างหน้าจัดการ FAQ เพิ่ม

## D-014 · ใช้ฐาน "ให้บริการตามที่ร้องขอ" แทนการขอความยินยอมเป็นเงื่อนไข (F-06) · ⚠️ ต้องให้ฝ่ายกฎหมายยืนยัน
- **คำถาม:** การรับเรื่องและติดต่อกลับควรอาศัยความยินยอม (มาตรา 19) หรือฐานอื่นตามมาตรา 24
- **การตัดสินใจ (ชั่วคราว):** หน้าลงทะเบียนเปลี่ยนจาก "ยินยอม" เป็น "รับทราบประกาศความเป็นส่วนตัว" ประกาศ v3 ระบุฐานมาตรา 24 · ระยะเวลาเก็บ · สิทธิทุกข้อ และช่องทางร้องเรียน ยังเก็บ version ของประกาศที่ผู้ใช้รับทราบในฟิลด์เดิม (`consent_version`) ไม่ขอความยินยอมแยกเพราะ MVP ไม่มีวัตถุประสงค์อื่น เช่น การตลาด
- **หลักฐาน:** แนวปฏิบัติ สคส. ระบุว่าความยินยอมเป็นฐานสุดท้ายหลังฐานตามมาตรา 24 · การถอนความยินยอมไม่กระทบการประมวลผลตามมาตรา 24 · มาตรา 23(3) ต้องแจ้งระยะเวลาเก็บ และมาตรา 37(3) ต้องลบเมื่อครบกำหนด โดยกฎหมายไม่ได้กำหนดจำนวนวัน (Q5)
- **ยกระดับถึง Fero:** ต้องให้ฝ่ายกฎหมายยืนยันฐานทางกฎหมาย ระยะเวลาเก็บ และข้อความประกาศก่อนใช้ข้อมูลจริง (ขวางการใช้งานจริง ไม่ขวางการทดสอบด้วยข้อมูลสมมติ)
- **ย้อนกลับได้:** ได้ ด้วยการออกประกาศ version ใหม่

## D-016 · ข้อความเจ้าหน้าที่ใน LINE ใช้ชื่อเจ้าหน้าที่เป็นผู้ส่ง และใส่เลขเคสเมื่อผู้แจ้งมีหลายเคส (F-14)

## D-017 · ข้อความอิสระของผู้แจ้งเข้าเคสที่เปิดอยู่เพียงเคสเดียวโดยอัตโนมัติ (F-03)

## D-018 · ลำดับงานระหว่างรอผลทดสอบ: ระลอก A ก่อน ระลอก B ยกระดับ
- **วันที่:** 2026-09-30 · **ที่มา:** `/po` ต่อจาก stage 9 · ตารางช่องว่าง `03-analysis.md` §6
- **คำถาม:** ระหว่างรอผลทดสอบกับผู้ใช้ ควรทำงานใดต่อ
- **ทางเลือก:** (ก) หยุดรอผลทดสอบ (ข) ทำระลอก A ที่ไม่ต้องใช้ข้อมูลลูกค้า (ค) เริ่มระลอก B ด้วยสมมติฐานเรื่อง hosting
- **การตัดสินใจ:** (ข) ทำ G1–G6 ตามลำดับความเสี่ยงต่อการใช้งานจริง: G2+G3 (PDPA) และ G4 (MFA) ก่อน เพราะเป็นข้อบังคับ แล้ว G1 · G5 · G6 ส่วน (ค) ปฏิเสธ เพราะการเลือก queue · storage · identity provider ผิดจะต้องทำซ้ำ
- **หลักฐาน:** SPEC §8 กำหนด PDPA และ MFA สำหรับ Admin เป็นข้อบังคับ · `08-verify-mvp.md` §6 ระบุเป็นเงื่อนไขก่อนใช้ข้อมูลจริง
- **ยกระดับถึง Fero:** ระลอก B ต้องการ hosting · identity provider · email gateway · LINE channel จากลูกค้า
- **ย้อนกลับได้:** ได้ งานจากผลทดสอบจะแทรกลำดับได้เสมอ

- **วันที่:** 2026-09-30
- **คำถาม:** จะทำ "บังคับ MFA สำหรับ Admin" (SPEC §8) อย่างไร ในเมื่อ SSO เป็น Phase 2 และยังไม่รู้ identity provider ของลูกค้า
- **ทางเลือก:** รอ OIDC · TOTP ในแอป · OTP ทาง SMS/อีเมล · WebAuthn
- **การตัดสินใจ:** TOTP ตาม RFC 6238 บังคับสำหรับ Admin และเปิดให้บทบาทอื่นใช้ได้ รายละเอียดใน ADR 0006
- **หลักฐาน:** RFC 6238 เป็นมาตรฐานเปิด ใช้กับแอป authenticator ทั่วไปได้ · SMS ต้องใช้ gateway ที่มีค่าใช้จ่าย (เข้าเงื่อนไขยกระดับ) และส่งข้อมูลส่วนบุคคลออกไปภายนอก
- **ย้อนกลับได้:** ได้ เมื่อมี OIDC จะออก ADR ใหม่มาแทน

## D-020 · กติกาการลบ/ทำให้ไม่ระบุตัวตน และคำขอของเจ้าของข้อมูล (G2, G3 · #19)
- **วันที่:** 2026-09-30 · **ที่มา:** รายละเอียดที่ต้องตัดสินระหว่าง build #19
- **การตัดสินใจ:**
  1. การลบตามคำขอและการครบระยะเวลาเก็บใช้ฟังก์ชัน `anonymise()` เดียวกัน: ล้างข้อความคำตอบ ข้อความสนทนา และบันทึกใน `case_event` ลบไฟล์แนบออกจาก storage เปลี่ยนหัวเรื่องเคสเป็นชื่อหมวด เก็บ metadata ของเคสไว้ใช้ทำรายงาน
  2. ผู้แจ้งที่ถูกลบข้อมูลแล้วจะเปลี่ยนสถานะเป็น `blocked` เพื่อไม่ให้ได้รับ push หรือประกาศอีก
  3. ลบได้เมื่อทุกเคสของผู้แจ้งปิดหรือยกเลิกแล้วเท่านั้น (รวมถึงเคสที่อยู่ในสถานะ "แก้ไขแล้ว")
  4. audit log บันทึกเฉพาะชื่อฟิลด์ที่เปลี่ยน ไม่บันทึกค่าข้อมูลส่วนบุคคล
  5. ระยะเวลาเก็บตั้งได้ 30–3650 วัน หรือปิดไว้ (ค่าเริ่มต้นปิด จนกว่าลูกค้าและฝ่ายกฎหมายกำหนด)
  6. คำขอของเจ้าของข้อมูลมีกำหนด 30 วันนับจากวันที่ได้รับ (มาตรา 30 · `01-research.md`)
- **ยกระดับถึง Fero:** ระยะเวลาเก็บจริงและกำหนด 30 วันต้องให้ฝ่ายกฎหมายยืนยัน (ต่อจาก D-014)
- **งานต่อเนื่อง:** รายการคำขอที่ใกล้/เกินกำหนดของทั้ง tenant ยังไม่มี (F-17)
- **ย้อนกลับได้:** การลบข้อมูลย้อนกลับไม่ได้โดยธรรมชาติ ระบบจึงบังคับยืนยันก่อนลบและบันทึก audit

## D-022 · ส่งประกาศต้องใช้ MFA และแจ้ง Admin เมื่อมีผู้เปิดใช้ MFA (#22 ข้อ 9)
- **วันที่:** 2026-09-30 · **ที่มา:** security review #22
- **คำถาม:** Supervisor ที่ใช้เพียงรหัสผ่านส่งประกาศถึงผู้แจ้งทุกคนได้ และผู้ที่รู้รหัสผ่านของ Admin ที่ยังไม่ตั้งค่า MFA จะตั้งค่า MFA ของตนเองแทนได้ก่อน
- **ทางเลือก:** (ก) บังคับ MFA ทุกบทบาท (ข) บังคับ MFA เฉพาะการส่งประกาศ และแจ้ง Admin คนอื่นทุกครั้งที่มีผู้เปิดใช้ MFA (ค) ลิงก์ตั้งค่า MFA ที่ Admin ออกให้
- **การตัดสินใจ:** (ข) เพราะการส่งประกาศมีผลกับผู้แจ้งทุกคนและใช้โควตาที่มีค่าใช้จ่าย ส่วนการแจ้งเตือนทำให้การตั้งค่า MFA โดยผู้อื่นถูกตรวจพบ (ค) เก็บไว้ทำพร้อม OIDC
- **ย้อนกลับได้:** ได้
